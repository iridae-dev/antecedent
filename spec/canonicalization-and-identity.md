# Canonicalization and identity rules

Status: normative. Specification version: 1 (`spec_version = 1`).

This document, with the three JSON Schemas beside it, is the specification of
the wire formats of three artifacts:

| Artifact kind | Metadata section | Schema |
| --- | --- | --- |
| `interface_contract_v1` | `interface_contract_meta` | `interface-contract.schema.json` |
| `evidence_ledger_v1` | `evidence_ledger_meta` | `evidence-ledger.schema.json` |
| `composition_bundle_v1` | `bundle.body` (plus `embedded.<node id>`) | `composition-bundle.schema.json` |

The key words MUST, MUST NOT, SHOULD and MAY are used as in RFC 2119. A
consumer that follows this document needs no code from the Antecedent
libraries: `spec/consumer/validate.py` is such a consumer, written from this
text with the Python standard library only, and the conformance fixtures in
`spec/conformance/` are generated by the Rust implementation and checked by
both. A change to any rule here is a change to the implementation, and the
repository's gate fails if either moves without the other.

## 1. What an identity is

An identity is a BLAKE3 hash (32 bytes, written as 64 lowercase hexadecimal
characters) of a canonical byte stream. It is never a hash of a rendering
(JSON text, `Debug` output, CBOR bytes of a larger structure): the stream is
built from typed fields exactly as described in section 3, so two parties that
agree on the declaration agree on the identity regardless of how either stores
it.

The identity of a thing changes whenever any field the stream includes
changes, and only then. Display labels are included where a field is part of
the declaration (a quantity's `variable_name` is in the stream); fields that do
not enter a stream are listed per kind below.

## 2. The artifact container

An artifact is one file.

```
magic             8 bytes   43 41 55 53 41 4c 00 00   ("CAUSAL\0\0")
container version u32 LE    1
manifest length   u32 LE    N
manifest          N bytes   one CBOR item (section 4)
sections          for each manifest section, in manifest order:
                    on-wire length  u32 LE
                    on-wire bytes
```

The manifest is a CBOR map with the fields `format_version`
(`{major, minor}`), `minimum_reader_version`, `artifact_kind`, `library_version`
(`{major, minor, patch}`), `artifact_id` (non-blank text), `sections` and
`provenance` (`{note}`). `artifact_kind` for the kinds in this document is the
externally tagged map `{"other": "<kind>"}`.

Each entry of `sections` is a map with `id` (unique), `content_type`,
`encoding_version`, `required`, `compression` (`null` or `"zstd"`),
`compressed_size` (the on-wire length), `uncompressed_size`, `blake3` (the
BLAKE3 hash of the on-wire bytes, as an array of 32 integers or a 32-byte
string) and `logical_schema`.

A consumer MUST refuse: a file whose magic differs; a container version other
than 1; a section whose on-wire length differs from its descriptor or whose
BLAKE3 differs from its descriptor; a duplicated section id; a section it
cannot decode. A consumer that does not implement Zstandard MUST refuse a
compressed section rather than skip it. Bytes after the last section MAY be
refused (the clean-room consumer refuses them). Producers of the conformance
fixtures write every section uncompressed and no trailing bytes.

The section checksums protect transport integrity only. They are not
identities, and a rewritten file with recomputed checksums is a valid
container: identity is checked as in section 6.

## 3. The canonical writer

A canonical stream is a byte string built from three framed field types:

* **word**: a `u64`, 8 bytes little-endian;
* **bytes**: a word holding the byte length, then the bytes;
* **text**: UTF-8 bytes framed as bytes. Text is compared and hashed as bytes;
  it is not normalized.

Composite fields are written from these:

* **texts**: a word holding the count, then each element as text;
* **real**: the IEEE-754 binary64 bit pattern as a word. `-0.0` and `0.0`
  differ, a NaN keeps its payload, and no rounding or formatting is involved.
  This is the **float-bit semantics**: a real is its bit pattern, wherever it
  appears, in streams and in the wire layouts (fields named `*_bits` and the
  numeric arrays of a synthesis hold the bit pattern as an unsigned integer;
  JSON consumers MUST read these as integers, not floats);
* **optional**: a word `0`, or a word `1` followed by the value.

A stream begins with its **domain tag** written as text, so two streams of
different kinds never coincide. The identity is `BLAKE3(stream)` with no key
and no derive-key context. Counts and enumerations are words; an enumeration is
written by the tag word this document assigns (never by a language-level
discriminant).

## 4. The CBOR profile

Metadata and manifests are single CBOR items (RFC 8949). A consumer MUST
accept definite-length encodings of unsigned and negative integers, text
strings, arrays and maps, `false`, `true`, `null`, and floating-point numbers
of any of the three widths; it SHOULD accept indefinite lengths. Map keys MUST
be text strings and MUST be unique. Bytes after the item are refused. A tag is
transparent. Metadata contains no byte strings, except that a manifest
`blake3` may be one.

CBOR is not hashed. Re-encoding a map in another key order or another integer
width does not change any identity in this document.

## 5. Versions, features, unknown fields

* Every metadata map has an integer `version`. A consumer MUST read it before
  interpreting any other field and MUST refuse any version it does not
  implement, including a newer one. This document defines version 1.
* `feature` names the format. A consumer MUST refuse a marker it does not know.
* `required_features` (interface contracts) lists capabilities a consumer must
  understand to interpret the artifact. Version 1 defines none; a consumer MUST
  refuse a non-empty list, because it cannot know what the entries require.
  Producers MUST NOT write entries this document does not define.
* A map with a field the schema does not list MUST be refused.
* A producer MUST write ports, sets, nodes and edges in the order given in
  section 6. An interface contract consumer MUST refuse an artifact that
  departs from it, so one declaration has one spelling of every identity
  input. The reference bundle reader is more lenient (it sorts nodes and takes
  edges as a set before recomputing); the clean-room consumer is stricter and
  refuses a bundle that departs from the order.

The order of the checks a consumer makes is: container, kind, version,
feature, required features, schema, structure (sorting, uniqueness, internal
references), semantic declaration rules, identities. The conformance manifest
names the refusal class of each negative fixture with these words:
`container`, `checksum`, `kind`, `unsupported`, `version`, `feature`,
`required_feature`, `schema`, `structure`, `semantic`, `identity`.

### 6.1 Interface contract

The identity version word is `1`. The **contract identity** is the stream:

```
tag "antecedent.interface_contract"
word 1                                       (identity version)
text component
word n_produced
  per produced port, sorted by name:
    text name
    quantity
    text semantic_identity
    support
    operations
    uncertainty
    calibration label
    texts measurement_models
    evidence
    texts provenance
word n_consumed
  per consumed port, sorted by name:
    text name
    quantity
    text semantic_identity
    support
    operations
    uncertainty
    word calibration_requirement             (not_required 0, measured 1)
    texts measurement_models
    word dependence                          (unconstrained 0, declared_evidence 1, disjoint_evidence 2)
    texts provenance
```

where

* **quantity** is: text `variable_id`, `variable_name`, `units`,
  `population_id`, `regime_id`, `functional_id`, `transform_id`; word role
  (treatment 1, outcome 2, covariate 3, mediator 4, selection 5, utility 6);
  word `horizon`; word count of conditions; per condition text `variable_id`
  then text `value_id`. (The wire field `version` of a quantity is not in the
  stream.)
* **support** is: word kind (real 1, non_negative 2, binary 3, interval 4,
  categorical 5); for an interval, word `lower_bits` then word `upper_bits`;
  for a categorical support, texts of the levels.
* **operations** is: word count, then per operation its tag word in ascending
  order (point 1, mean 2, law 3, draws 4, joint_draws 5, covariance 6,
  interval 7, posterior 8).
* **uncertainty** is: word `0` for none, or word `1`, text meaning, text
  paradigm.
* **calibration label** is: word tag (none 1, point_only 2, unmeasured 3,
  measured 4, inherited 5), followed for `measured` by text `record_id` and for
  `inherited` by text `input`.
* **evidence** is: word `0` when undeclared, or word `1`, word count, then
  each source identity as text (64 lowercase hex characters), ascending.

The **artifact identity** is the stream: tag
`antecedent.interface_contract.artifact`, word `version`, text `feature`,
texts `required_features`, text `contract_identity`.

Structural rules a consumer applies before the identities: ports are sorted
by name and distinct within each direction; operations are in canonical order;
`measurement_models`, `evidence.sources`, `provenance` and categorical levels
are sorted and distinct (byte order of the UTF-8 text); `measurement_models`
and `sources` are 64 lowercase hex characters; the stated paradigm of an
uncertainty is the paradigm of its meaning (parameter_posterior,
causal_functional_posterior, posterior_predictive and interventional_predictive
are `posterior`; estimator_sampling is `sampling`; bootstrap is `resampling`;
empirical_outcome is `empirical`).

Semantic declaration rules a consumer applies: every identity field of a
quantity is non-blank and conditioning is sorted by `variable_id` and distinct;
an interval support has finite bounds with `lower <= upper`; a port declares an
uncertainty meaning exactly when it offers or requires one of law, draws,
joint_draws, covariance, interval or posterior; a posterior operation has a
posterior-paradigm meaning; a point-only label does not accompany such an
operation; a measured label has a non-blank record and accompanies an interval
or posterior operation; an inherited label names a consumed port of the same
contract; a consumed port that requires measured calibration requires an
interval or posterior operation.

### 6.2 Evidence ledger

The artifact identity is the stream: tag `antecedent.evidence_ledger.artifact`,
word `version`, text `feature`, text `head`, text `state_digest`, word count of
operations, per operation text `kind` then text `id`, word count of syntheses,
and per synthesis: text `result`, text `method`, texts `sources`, then each of
`estimates`, `variances`, `covariance`, `tau_support`, `tau_probabilities`,
`values` as a word count followed by each element as a word, then `rho_lo`,
`rho_hi`, `prior_mean`, `prior_variance` as optional words.

Operation identities (`operations[i].id`), the head and the state digest are
the replay identities of the ledger: each operation's identity chains the
previous operation's, so replay requires the ledger's overlap rules, which this
document does not restate. A consumer that does not implement the ledger MUST
verify the artifact identity above (which binds every operation identity, the
head, the state digest and every synthesis) and the structural facts: the head
equals the identity of the last operation, operation identities are distinct,
and every synthesis is bound to a result and to sources that operations
created. It MAY recompute syntheses it implements; the `fixed_effect_inverse_variance`
values are `[estimate, variance, Q, w_1 .. w_n]` with precision `p_i = 1 / v_i`,
`total = sum(p_i)`, normalized weights `w_i = p_i / total`,
`estimate = sum(w_i y_i)`, `Q = sum(p_i (y_i - estimate)^2)` and
`variance = 1 / total`, sums taken in study order, agreeing to a relative
`1e-12`. Such a
consumer MUST NOT report that it replayed the ledger.

### 6.3 Composition bundle

A bundle is a directed graph. The body lists nodes (sorted by `id`, distinct)
and edges (`from` the upstream node, `to` the dependent node, sorted by
`(from, to)` and distinct). An embedded node's bytes are the container section
`embedded.<id>`; a bundle has exactly one section per embedded node plus
`bundle.body`.

* **node digest**: tag `antecedent.composition_bundle.node.v1`; text `id`,
  text `kind`, text `identity`. For an embedded node: text `embedded`, then
  text of the lowercase hex BLAKE3 of the section bytes (the unframed hash of
  the bytes). For a reference node: text `reference`, text `identity`, text
  the **requirement string**, word count of facts, per fact (ascending key
  order) text key then text value, word count of inspected values, per
  inspected value text key then the real. The requirement string is
  `provider|<provider_id>|<snapshot_id>|<request_fingerprint>` or
  `data|<snapshot_id>|<digest>`.
* **link digest** of node `n`: tag `antecedent.composition_provenance.link.v1`;
  text `<id>@<node digest>`, text the **stage** of the node's kind (table
  below), texts of the link digests of its parents. A node's parents are the
  `from` nodes of the edges that name it as `to`, in ascending order of `from`.
  The graph MUST be acyclic.
* **edge digest**: an edge's `upstream_digest` is the link digest of its
  `from` node.
* **bundle identity**: tag `antecedent.composition_bundle.v1`; word node
  count; per node (ascending `id`) text `id`, text node digest, text link
  digest; word edge count; per edge (ascending `(from, to)`) text `from`,
  text `to`, text `upstream_digest`.

A changed upstream node changes its link digest and so the link digest of
every node downstream of it, every edge digest on those paths and the bundle
identity.

Node kind to stage (the stage written into the link digest):

| Kind | Stage |
| --- | --- |
| `causal_contract` | `causal_contract` |
| `execution_or_fit` | `distribution_artifact` |
| `external_claim` | `external_provider` |
| `attestation` | `external_provider` |
| `evidence_relationship` | `evidence` |
| `quantity_coordinates` | `evidence` |
| `support_trust_calibration` | `evidence` |
| `distribution` | `distribution_artifact` |
| `transformation` | `transformation` |
| `decision_contract` | `decision_contract` |
| `decision_result` | `claim` |
| `sensitivity` | `sensitivity_input` |
| `study_ranking` | `study_ranking_provider` |
| `rollout` | `transformation` |
| `inverse_query` | `claim` |
| `repair_report` | `evidence` |
| `recalculation_receipt` | `evidence` |
| `frozen_scores` | `distribution_artifact` |

The bundle format does not interpret embedded bytes. A bundle consumer that
verifies embedded nodes does so with the verifier registered for the node's
kind; a clean-room consumer verifies the Merkle structure only and MUST report
embedded content as not interpreted.

## 7. Conformance

`spec/conformance/manifest.json` lists the fixtures. Each entry has `file`,
`kind`, `expect` (`accept` or `reject`) and, for a reject, `reject_class`
(section 5); an accepted entry also has the recomputed `identity` and a
`meta_json` rendering of the decoded metadata. `blake3_vectors.json` lists
hash vectors for inputs of the form `byte[i] = i mod 251`, produced by the
reference BLAKE3 implementation; a consumer MUST pass them before trusting any
identity it computes.

A consumer conforms if it accepts every `accept` fixture with the listed
identity, rejects every `reject` fixture with the listed class (or an earlier
class in the order of section 5 when the artifact has several defects, which
the fixtures do not), and rejects any single-field mutation of an accepted
fixture that changes a semantic field, an identity, a version, a feature
marker or the field set.

Regenerating the fixtures is a deliberate act: set
`ANTECEDENT_REGENERATE_CONFORMANCE=1` and run the
`specification_conformance` test of the `antecedent` crate. The same test
refuses a repository state in which the committed fixtures differ from what
the implementation produces, or in which this document's tables differ from the
implementation's vocabularies.
