# Embed Antecedent in an application or agent

Your application can submit a causal question, read what Antecedent compiled before anything runs, and receive either a claim with its limits or a typed refusal. This guide is the contract between your code and the library: the schema your requests and records follow, the status and refusal codes your branches switch on, and the rules for resources, cancellation and callbacks.

Antecedent supplies the causal computation and its contracts. Your host supplies planning, tool use, permissions and the policy for acting on an answer. Antecedent ships no planner, tool loop, prompt or memory, so the same interface serves a service, a notebook tool or an LLM tool layer. For a worked host, read [use a causal analysis as a component in your application](../../tutorials/application-component.md).

The host contract has four parts:

1. a versioned [JSON Schema](#the-schema) for requests, contracts, claims, refusals and the `supported`, `partial` and `unsupported` statuses;
2. [stable status, refusal and error codes](#statuses-refusals-and-error-codes) shared by Rust and Python;
3. [resource, cancellation and callback rules](#resources-cancellation-and-callbacks) a host must follow;
4. [artifact loading and versioning](#loading-artifacts) rules.

A runnable [reference host](#reference-host) exercises all four with no agent logic.

## The schema

The schema is `crates/antecedent/schemas/host_contract.schema.json`, JSON Schema
2020-12, identified by `urn:antecedent:host-contract:<version>` and carrying
`x-contract-version`. It is generated by `scripts/generate_host_schema.py` from the
registries and enums that own each vocabulary (the reason-code registry, the claim and
capability enums, the support-matrix labels, the exception declarations and the durable
artifact format). Nothing in it is written by hand. Three checks fail when it drifts:
`python3 scripts/generate_host_schema.py --check`, the Rust test `host_contract` (compares
it with the compiled types and registries) and `python/tests/test_host_contract.py`
(compares it with the installed package).

Read it from either language:

```rust
let schema = antecedent::host::host_schema()?;      // serde_json::Value
let text = antecedent::host::HOST_SCHEMA_TEXT;      // the committed bytes
```

```python
from antecedent import host
schema = host.schema()          # dict; host.schema_text() is the committed bytes
```

The contract version moves only when a consumer must change (a member removed or
renamed, a meaning changed). New enumeration members and new optional fields do not move
it, so a host validates against the version it was written for and ignores what it does
not know. Check `x-contract-version` at start up.

What the schema defines:

| Definition | Meaning |
| --- | --- |
| `analysis_request` | what a host submits: a query named by its support-matrix label, a graph, data (column names or a reference, never a callback) and options (inference, seed, threads, bootstrap) |
| `causal_contract` | the immutable record of what was compiled: identities, graph class, structure source, support status and the four reasoning slots |
| `claim_envelope` | the portable claim over a contract and one execution: kind, value, three domains, execution identity, evidence references |
| `operation_report` | the capability report read before running: applicability, readiness, blockers, next actions |
| `refusal` | a typed refusal: registered code, exception family, message, remedy |
| `host_response` | exactly one of a claim or a refusal, with its status |
| `artifact_expectation` | what a consumer retains independently of the bytes |

A request carries no executable content. Data stay in the host; a provider or callback
is supplied in code, never named in a request (see [callbacks](#callbacks)).

## Statuses, refusals and error codes

Every claim and every operation has one of three statuses, decided by one rule in Rust
(`antecedent::host::HostStatus`) that Python reads through the native module, so the two
cannot differ:

| Status | A host may |
| --- | --- |
| `supported` | use the claim as stated. The route is licensed, identified under the declared structure, executed, and nothing contradicts it. |
| `partial` | use only what the record says: an identified set, an open obligation, an unreviewed graph, an unevaluated domain. Relay the limit with the answer. |
| `unsupported` | not use it. The record is a refusal, or a domain is contradicted or outside the declared scope. |

The rules, in order, for a claim: a `refusal` kind, or any domain `contradicted` or
`outside_scope`, is `unsupported`; an `incomplete` or `bounds` kind is `partial`; an
`associational` claim, which is noncausal and reports identification as `not_claimed`, is
`supported` when it is evaluated and `partial` otherwise (it is never counted as an
identified, causal claim, and its record states `causal: false`); an
identified and evaluated claim is `supported` (an `unknown` support domain means no
empirical check ran, stays visible in the domains and does not demote it); anything else
is `partial`. For an operation: an impossible or unlicensed cell, or a failed empirical
check, is `unsupported`; a licensed cell with met bindings (`executable`) is `supported`;
the rest (review pending, an assumption or binding missing, a check not run, a resource
limit, unknown support) is `partial`. A status is advice about use, not a verdict about the
world: `supported` does not certify the assumptions.

A claim's support domain is `limited`, and its status `partial`, when the computation itself
flagged a weakness the answer rests on: an overlap clip or trim that bound
(`limited:overlap`), dropped bootstrap replicates (`limited:bootstrap`), weak sampler
diagnostics (`limited:mcmc`), or a failed non-support refuter such as a placebo
(`limited:refuter.<id>`). The result's diagnostics carry the numbers. A failed overlap or
positivity check still reads `contradicted`.

```python
report = prepared.inspect()
host.inspection_status(report)                    # before running
host.claim_status(result.inspect().contract["claim"])   # after
```

```rust
let status = antecedent::host::HostStatus::of_operation(&contract.capability());
let status = antecedent::host::HostStatus::of_claim(&claim);
```

A name outside the registered vocabularies is `unsupported`: a host that cannot read a
record must not use it.

### Refusal codes

A refusal carries a registered runtime-refusal code (`parity/reason_codes.toml`, entries
with `applies_to` containing `runtime_refusal`). The code is part of the contract: it is
checked at compile time in Rust (`unsupported_reason!`), checked at construction in Python
(`CausalUnsupportedError(reason_code=...)` raises `ValueError` for an unregistered code),
and the Python test suite asserts that every code written anywhere in the package or the
examples is registered and that the native list equals the registry. Codes are append-only;
a code is not renamed or reused. Rust and Python share the same list:

```python
host.refusal_codes()                       # frozenset of registered codes
```

```rust
antecedent::host::refusal_code(&error)     // Option<&str>, only ever a registered code
```

A refusal is not a failure to be retried. It names what the caller can change to proceed
(`remedy`, when it states one) and, through `next_actions` in the capability report, a
licensed neighbor. Never substitute a different route silently.

### Refusals and failures in Python

A scientific refusal and an operational failure reach your code differently. `ant.estimate(study)` returns an `Outcome`. When the question cannot be answered under the declared structure, the outcome is not accepted: `outcome.accepted` is false, `outcome.answer.kind` is `"refused"` and `outcome.refusal` carries the `code`, `message`, `remedy` and any `next_actions`. Nothing is raised. A cancellation, a resource limit, a corrupt artifact or a callback failure is an operational failure and raises a `CausalError`. To turn a refusal into the registered record, raise it and classify it:

```python
try:
    outcome.refusal.raise_error()
except ant.CausalError as error:
    record = host.refusal_record(error)
```

`ant.prepare` also retains a refusal on the study (`study.refusal`) when the structure you declared cannot identify the question, so a host can decline before running anything.

### Error families

A failure that is not a refusal (invalid input, a resource limit, a cancellation, a
corrupt artifact) still classifies into a stable family. The families are the exception
classes of the Python package and the variants of `CausalError`, named by code in the
schema's `error_family` list and `x-error-families` table:

| Family | Host reading |
| --- | --- |
| `unsupported` | a refusal; read `reason_code` and `remedy` |
| `not_identified` | the question has no identified estimand under the declared structure; the message says whether the search stopped at a budget |
| `review_required` | a graph review is pending; answer it, then retry |
| `cancelled` | the study was cancelled; no claim exists |
| `resource` | a memory, worker or budget limit; retry with a larger lease or a smaller problem |
| `serialization` | an artifact or container could not be read or failed an integrity check |
| `data`, `graph`, `compile`, `validate`, `state`, ... | invalid input or inconsistent state; fix the request |

```python
record = host.refusal_record(error)      # {"status", "family", "reason_code", "message", "remedy"}
host.error_family(error)                 # equal to Rust's family for the same failure
```

```rust
antecedent::host::refusal_record(&error)     // serde_json::Value, same shape
antecedent::host::error_family(&error)       // &'static str
```

`family` classifies every failure; `reason_code` is `None` unless the error carries a
registered code. Python-only narrowings (a type error, a value error, a structured
refusal) report the coarse family Rust uses.

## Support cells and their neighbors

A host can ask the support matrix about any coordinate (`query:graph:structure:inference:validation`)
without preparing or fitting anything. `host.support_cells()` lists every licensed coordinate, and
`host.support_cell_report(coordinate)` classifies one:

```python
from antecedent import host

cells = host.support_cells()                 # every licensed coordinate; a pure read
report = host.support_cell_report("TransportQuery:Dag:explicit:Frequentist:none")
print(report["status"])                      # licensed, refused or not_applicable
print(report["message"][:60])                # the blocker text; None for a licensed cell
nearest = report["neighbors"][0]
print(nearest["coordinate"], nearest["changed"], nearest["required_action"])
assert nearest["coordinate"] in cells
assert host.support_cell_report(nearest["coordinate"])["status"] == "licensed"
```

`neighbors` are the licensed cells of the same graph class that change explicit premises, nearest
first. Each names the `changed` axes (`axis`, `from`, `to`) and the `required_action` a caller
would take. They are alternatives the caller chooses between, never an automatic fallback, and a
licensed cell has none. A malformed coordinate or an axis value outside the matrix raises
`CausalValueError`. Licensing a cell does not establish empirical support or interval calibration;
see the [support matrix](../../support-matrix.md).

## Resources, cancellation and callbacks

### Threads and resource leases

Parallelism is a budget on an execution context, not a global setting.

* A study runs under an `ExecutionContext` (`ExecutionContext::production(seed, threads)`
  in Rust, `ant.Execution(threads=...)` in Python). `threads` omitted or `0` takes
  `min(available_parallelism, 16)`; an explicit positive value pins the study to that many
  workers even above the cap. Nested parallel work inside a worker sees one thread, so
  a budget is never multiplied.
* Two studies share a machine through one `AdmissionPool` installed on each context
  (`ExecutionContext::with_admission`). Every parallel batch takes one atomic lease on the
  pool for its workers and scratch bytes (`ExecutionContext::admit_scratch`) and returns it
  when the lease drops, including on error and unwind. A batch the pool cannot fully fund
  runs with fewer workers and, when it cannot fund even one worker's share, is refused
  (`ScratchRefusal::PoolShort`) immediately. A host that wants to wait for a root lease
  uses `ExecutionContext::acquire_admission_bounded`, which waits up to a stated bound and
  ends early on cancellation.
* Device bytes are a separate account (`DeviceReservationPool`) and no accelerator is
  promoted; a CPU study never decrements it.
* Process-global pools the library does not own cannot be resized per study. Dense linear
  algebra uses the process-wide BLAS/Rayon pool and a neural learner is serialized behind a
  lock; see the [thread inventory](../../architecture/thread-inventory.md) for each entry and its
  disposition. A host that must bound those sets the process pool once at start up.
* Size the budget for the problem: a refusal with family `resource` means the lease or
  memory limit was too small for this request, not that the question has no answer.

### Cancellation

Cancellation is cooperative. A host holds a `CancellationToken` (`ant.Execution(cancel=token)` in
Python, the context's `cancellation` field in Rust), passes it with the call, and calls
`cancel()` from any thread.
The engines poll it at named boundaries (table scans, solvers, resampling, search, chains,
providers) and return `cancelled` when the bounded call returns to a boundary. A
cancellation therefore takes effect at the next boundary, not instantly.

* A cancelled call returns no claim and no partial result as a claim: publishing a partial
  result as a claim is refused. Treat `cancelled` as "nothing was answered".
* Leases are returned on cancellation (workers and scratch bytes, device reservations,
  spill records) before the call reports stopped.
* From Python, `KeyboardInterrupt` raised in the main thread cancels the running native call
  and is what the caller sees; `except CausalError` does not swallow it.
* A provider that cannot be interrupted is admitted as isolated or refused. See below.

### Callbacks

A callback (a provider, an intervention program, a design utility) is code the host runs
inside the library's call. The contract:

* A request and an artifact never name code. A declaration describes a provider (identity,
  version, dependencies, contract); the only way a provider runs is that the host passes an
  implementation in code, and the library refuses a provider whose identity differs from
  the declared one with zero invocations.
* Planning and verification invoke nothing that has side effects. A side-effecting
  callback needs `allow_side_effects` and is retried only under an idempotent contract.
* Callback output is data: it is accepted only after validation (finite, in support, the
  declared count), and a hostile value is refused whole. Native trust cannot be minted by
  metadata or by a stored artifact.
* Bounds on invocation count and output size are exact. The wall-clock bound is enforced
  after the call returns: a callback that never returns is not interrupted. A host that
  must survive a hung callback runs it in a process it can terminate.
* A closure runs with the host's authority and is not sandboxed. Supplying a provider is
  the host's act of trust. Never construct a provider from text a user or a model produced.
  A Python callable that raises is re-raised unchanged (or chained as `__cause__`), so a
  traceback into user code survives.

The full threat model, the bounds on every deserialization entry point and the tests that
pin them are in [callback security](../../callback-security.md); the behavior is in
[provider callbacks](../../provider-callbacks.md).

## Loading artifacts

An artifact is a checksummed container: bytes, not code. Loading never runs a callback, never recreates a live study and never imports anything the bytes name. [Save, hand off and accept results](artifacts-and-handoff.md) covers the producer and consumer workflow; the rules a host enforces are these:

* Keep the expectation apart from the bytes. `ant.load(bytes(artifact), expected=expectation)` binds the load to the identity your producer retained; container metadata never supplies it.
* Read acceptance, not just success. A load that decodes can still be partial. Use `acceptance.identity_bound` together with `acceptance.answer_available` in Python, or `accepts_as_claim()` in Rust. A malformed or altered container is a `serialization` error.
* Bound untrusted input. Reject oversized uploads before calling the library, and do not widen a bound to accept one.
* A loaded result is immutable. To change anything, compile and run again: `ant.rebind` followed by `ant.estimate` re-executes the same program on new data and keeps the earlier result fixed.
* Staleness is a question for the host, not a timer in the library. Compare new data with a stored artifact or plan using the [staleness diagnostics](../staleness.md) and act on the typed recommendation (reuse, refresh, re-identify, refuse).

### Versioning

Three versions are separate and a host should record all three:

| Version | Where | Moves when |
| --- | --- | --- |
| Host contract | `x-contract-version` in the schema | a schema consumer must change |
| Durable artifact format | `x-artifact-format` in the schema (`antecedent_io::STABLE_FORMAT`) | the bytes on disk change; a reader migrates older supported formats forward and refuses a format newer than it understands (`minimum_reader_version`) |
| Library package | the crate and wheel version | any release; a package bump alone does not change artifact bytes |

Artifacts written by an older supported format load and migrate; an artifact needing a
newer reader than the host has is refused, not guessed. Pin the library version a service
was validated with, and treat a wire change in the artifact format as a migration (see the
[artifact format](../../artifacts.md)). Registered refusal codes are append-only, so a host that
switches on a code keeps working across releases.

## Reference host

[Use a causal analysis as a component in your application](../../tutorials/application-component.md) walks through a host that prepares a request, reads the plan, handles an answer and a typed refusal, applies its own acceptance policy, branches onto changed data and consumes an artifact. `examples/rust/reference_host.rs` and `examples/python/reference_host.py` are the minimal contract host. Each:

1. checks the contract version it was written for;
2. compiles a request and reads the status before running;
3. runs only what is not `unsupported` and reports the claim with its status;
4. reports a refusal as a record with code, family and remedy, never as a number;
5. stores the artifact beside a separately retained expectation and accepts bytes only against it, refusing altered bytes and a different request's identity.

```bash
cargo run -p antecedent --example reference_host
python examples/python/reference_host.py
```

A real host adds its own transport, authentication, queueing and policy on top of this. None of that belongs in the library, and none of it changes what a claim means.
