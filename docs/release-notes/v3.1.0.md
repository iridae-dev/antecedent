# Antecedent 3.1.0

Antecedent 3.0 prepared a study and kept the claim with the evidence behind it. You could already decide once every outcome had a weight. 3.1 is for the decision you still could not write down, because the rate at which you would trade one outcome for another is a range you can defend and cannot pin to one number.

You declare that range on the study that estimates the outcomes. The result says which actions win at every value in the range, which can win somewhere in it, and the value where the choice changes. The same study can estimate a covariate slope from the trial itself, or fit models you already trust. A stream of marked events can say how many later events one event produces, and what one added event is worth under a structure you declared.

A result is still a claim. It carries its identification, support, uncertainty, and calibration. Running the study does not make the claim stronger.

## Highlights

- **New:** a decision over a range of trade-offs, attached to the study that estimates it; a CUPED slope estimated from the same trial; models you supply for a trial-to-target transport or for joint treatment cells; marked events, the later events they produce, and the value of one added event. The worked case is [Choose a discount when the cost of a return is a range](../tutorials/decide-across-trade-offs.md).
- **Changed in claims:** a law that names no coordinates it supports is missing evidence. A recalculation drops a stage whose input was removed. A restated claim stays as strong as the evidence it cites.
- **If you are on 3.0:** [Migrate from 3.0 to 3.1](../migration-3.1.md). Calls that used to sit beside the study still run and warn. They are removed in 4.0.

Each section below says what you were doing, what you can declare now, and what the result means.

## Decide when the trade-off is a range

A decision in 3.0 ranked actions under weights you had already chosen. That is the right answer when the weights are known. It answers a question you did not mean to ask when the disagreement is the weight: the cost of a return, the value of a later outcome, how much of one harm you would accept for one unit of benefit.

Declare that disagreement as a set of values. `decision.Contract(value=decision.Value(...), policy=)` takes the outcomes the study estimates and the trade-offs you are willing to consider. You then read four things:

- which actions are best at every value in the set
- which actions are best at some values and not at others
- how far each action can fall behind the best one
- the value where the preferred action changes

The set is the assumption you wrote down, and the result treats it as that assumption. Putting a probability on the set would be a further assumption, one you have not supplied.

When the value is a straight line in those trade-offs and the goal is expected value, the answer is exact. When the value bends, as with a discount factor, a breakpoint, or a risk attitude, or when the goal is something other than expected value, the answer is a certified enclosure: every region it marks as best is best, and it reports how much of the set it had to leave undecided.

If the graph is an equivalence class rather than one graph, a member that is not identified stays unidentified. `ClassPrior` is how you weigh the members that are identified: the same weight on each, weights from pairs you supply, an exact limit, or a sample.

Leave `value=` off and the contract is the decision you already had. It constructs and evaluates as before.

The discount example lets the cost of a return run from 10 to 60 dollars and shows the cost at which the choice flips: [Choose a discount when the cost of a return is a range](../tutorials/decide-across-trade-offs.md).

## Attach that decision to the study

3.0 could compile a decision from the rows that estimate its inputs. You can now treat that decision as its own question on the study.

You name the estimates the decision needs. Antecedent checks the decision first. When that question is not supported, the study stops before those fits. When the fits run, each estimate keeps the claim it earned, and the decision cites those claims.

What gets saved is the list of estimates you named, in that order, together with the decision you declared. Change the list or change the decision and the saved result is a different one. A decision you could already run returns the same numbers.

`contract.compile(prepared)` does the check, before any fit. `compiled.execute()` runs the fit and the decision. Every decision result includes `standing` and `statement`. `best` means one action ranks alone in first place.

In Rust, `Study::compile_decision_program` compiles a decision on the study's result. `Study::compile_evsi_program` compiles a request for the value of collecting more information. If your code still calls `Study::compile_for_decision` or `Study::compile_for_evsi`, switch to those names. The old calls return the same plan and warn.

You can save the study and estimate it again later. `save_compiled_study` writes it. `compiled_study.open_study` on those bytes estimates again, and the new estimate matches the claim you sealed. Any other file opens without an estimate to resume. `load` of the analysis artifact, passed the identity you kept, returns the claim with `study` set to `None`.

The calls are in [Migrate from 3.0 to 3.1](../migration-3.1.md).

## Narrow the range from choices already made

A range you type in is as wide as the disagreement you brought. Recorded choices are a way to shrink it. If you have the choices and the attributes of the options people were choosing among, you can ask which trade-offs those choices still permit.

`antecedent.decision_learning` reads the records.

`PreferenceCompatibleSet` returns every trade-off at which each recorded choice was at least as good as the options that were turned down. You asked for that set of assumptions. It is not a confidence interval.

`PreferenceChoiceModel` fits a conditional logit. You get the trade-off rates and a delta-method interval. No coverage record backs the interval, so the claim you can carry forward is the point. The fit is an association between the recorded choices and the attributes of the options.

`AcceptedPreferences` stores a value after you have reviewed it, with a version. A later contract can take that stored value as `value=`. Opening the stored handle recomputes it from the same records.

## Let the trial estimate its own covariate slope

A CUPED adjustment uses a column measured before assignment to pull noise out of a randomized effect. You can still pass a slope you fixed before seeing these outcomes, with `cuped=FixedCUPED(...)`. On a Bernoulli trial the study can estimate the pooled slope from the same rows, with `estimated_cuped=EstimatedCUPED("baseline")` on `RandomizedEffect`. The estimator is `randomized.estimated_cuped_ht_itt`. Read the fitted slope from `adjustment_coefficient`.

`ancova_covariates=` is the other adjustment, the one that fits the covariates in the same regression as the treatment. That call is unchanged.

On a Bernoulli or complete design of at most twenty units, set `exact_randomization_test=True` on the same query. Antecedent lists the assignments and tests the sharp null that the treatment changed nobody's outcome. Read `randomization_p_value` and `randomization_allocations`. Those two fields are the result.

If your code still calls `estimate_cuped_effect`, `estimate_ancova_effect`, or `experiment.exact_randomization_test`, move the declaration onto `RandomizedEffect`. The old call warns.

[Experiment designs](https://github.com/iridae-dev/antecedent/blob/v3.1.0/examples/python/experiment_designs.py) runs the estimated slope and the exact test.

## Use models you already trust

You may already have a model for the outcome and a model for who is treated. A side call could fit both and hand you a number. That number arrived without the study's adjustment set, without a record of which rows each fit was allowed to see, and without a claim.

Declare the models on the study. The adjustment set, the rows, and the claim stay with the study.

`analyze_trial_aipw` carries a trial effect to a target population with those models. `analyze_joint_cells` returns one point for each combination of several binary treatments. Both results say the models were yours and were not checked. In Rust the same two fits are `Study::compile_trial_aipw_learners` and `Study::compile_joint_cells_learners`.

A smoothed dose-response needs a predictor you can save and load again. A function that exists only in the running Python process is refused.

`analyze_discovered_transport` runs a structure search and reports every member it finds. You choose which member to carry forward. `PerPopulationDiscovery.compiled_run` does the same when each population is searched on its own. If your code still calls `discover_and_transport` or `PerPopulationDiscovery.run`, switch to those. The old call warns.

See [Use your own outcome and treatment models](../tutorials/external-learners.md). The old and new forms are in [Migrate from 3.0 to 3.1](../migration-3.1.md).

## Ask what one more event is worth

3.0 forecast arrivals by type and could decide on that forecast. 3.1 asks three further questions of the same kind of stream. Python reaches all three through `antecedent.events.prepare`.

Some events carry a label, and you group those labels into prototypes. `forecast.marked_event_process` fits a Hawkes kernel on the prototypes. You get the likelihood of the history you observed, the kernel that fits it best while keeping offspring from growing without bound, and the paths a kernel you named would draw.

`forecast.hawkes_excitation` counts the later events one event brings with it: the ones it produces directly, and the ones those produce in turn. You can ask for that count on a horizon, or over the lifetime. You can also ask whether the direct count still holds when the background rate of new events follows a trend you declare. Where it holds, you can compare two times at which you might add an event.

Where that check agrees, `forecast.hawkes_parameter_bridge` asks what one added event does under a structure you declared. The structure may be one graph, an equivalence class read through the graphs it allows, a list of candidates, a posterior over graphs, or a cyclic system whose edges are lags.

Some members of that structure include the edge from the event to the outcome, and some do not. The first contribute the stream with the added event. The second contribute the same stream without it. You receive one mixture of those two readings. You can also price what it is worth to watch the stream before you act, for the structure as a whole and for each member.

All three answers are points. None of these routes has a coverage record for an interval, so none of them claims one.

How many event types you can name is capped by the operation budget. One event study accepts up to 63 intervention worlds.

The walkthrough is [When outside events interrupt a launch](../tutorials/event-driven-launch.md).

## Open the file you actually wrote

Passing an artifact along is only useful if the next reader can tell that the file they opened is the file you wrote. Keep an identity next to the bytes, and pass it in when you load. In Python the argument is `retained_identity=`. `antecedent.artifacts.artifact_identity(data)` computes it from the bytes. The loader compares the file with that identity before reading it. A file that differs is refused with `external_binding_mismatch`.

A loader called with neither `retained_identity=` nor an expected identity still reads the file, and it warns. That form is removed in 4.0.

A loaded law can also claim to cover more than it stated. A coordinate the support mask never mentions is missing evidence, unless the law was produced by a run Antecedent itself recorded. Pass `supported=` for the coordinates your provider covers. A law from an outside provider that arrives with no mask is missing evidence on every coordinate.

## Drop work that lost an input

A recalculation used to rebuild a stage whenever some earlier input had changed. That included a stage whose own input had been removed, as long as some other input had changed first. Antecedent now drops that stage. In Rust the call is `RecalcPlan::plan`.

The receipt records which rule wrote it. Version 1 is the earlier rule, and its bytes are the bytes a receipt had before this release, so an older reader still accepts it. Version 2 is this rule. It is written when a removed input sat beside some other change, and a reader from before 3.1 refuses it. A receipt you stored before this release keeps its identity and still replays.

The same standard applies when a claim is restated. It stays as strong as the evidence it cites. A bridged claim carries the obligations its source left open. A member of a structure that is only partly identified stays partly identified. An interval with no positive standard error is reported as not measured. The [changelog](https://github.com/iridae-dev/antecedent/blob/v3.1.0/CHANGELOG.md) lists each place this was fixed.

Compiling some studies produces a new identity once. Where the changelog says a stored artifact still verifies, it still verifies. [Migrate from 3.0 to 3.1](../migration-3.1.md) has the calls and the receipt rule.

## Evidence follows what ran

A coverage record now backs the unit its test executed. No cell, graphless row or capability lists its records by hand any more, so a record cannot back a unit it never ran ([ADR 0031](https://github.com/iridae-dev/antecedent/blob/v3.1.0/adr/0031-unified-evidence-records.md)). Every unit supported in 3.0 keeps its scientific checks, and its calibration does not drop from records to a reason, except where this section says so.

Narrowed:

- **Bayesian interference cells.** On 44 cells (`InterferenceQuery`, Bayesian, every graph class, structure and validation mode), the Dirichlet cluster bootstrap is not supported at 50 or more clusters per arm. The cells no longer claim that coordinate. Its two coverage records per cell stay in the registry as measurements no unit admits.
- **`composition.release_boundary_fixture` and `evidence_ledger.overlap_accounting`.** The 18 pooled-mean coverage records measure the pooled interval. That interval comes from `evidence_ledger.pooled_interval`, which now holds them. Neither of these two capabilities ever produced it.
- **`measurement.model_contract`.** The 7 measurement records belong to the measurement model each one executed. The contract is the shared interface and claims no interval.

Retired: none.

Moved without a change in support: the interference grid's records belong to the graphless exposure-contrast rows they execute. Eleven capability records hand their evidence to the unit they run through, for example `cohort_decision.mean_contrast` to `cohort_decision.interval` and `counterfactual.transport_sampled` to `counterfactual.transport_sampled_interval`. `parity/evidence_resolutions.toml` lists every move with its reason.

Corrected: on an explicit ADMG or temporal ADMG, a Frequentist counterfactual with bootstrap replicates reports a normal interval from the bootstrap standard error. 3.0 described it as point only. The interval is not measured.

A coverage record whose test reaches no supported unit backs no claim. `parity/unit_index.json` lists it as unadmitted, together with the units its test refused.

## How to read the claims

The inventory that follows is one entry per question this release answers. Read the scope before you take the route as answering your question.

| Phrase | Meaning |
| --- | --- |
| Point only | An exact or plug-in point. No interval is claimed. |
| Statistical interval | An interval with a coverage record at its own coordinate. |
| Structural envelope | A range over structural scenarios you supplied. Not a confidence interval. |
| Assumption range | A range over a sensitivity or trade-off set you declared. Not a confidence interval. |
| No numerical claim | Identification, inspection, or replay. No number is the answer. |
| Not measured | An interval may be reported. No coverage record backs it, so the claim stays the point. |
